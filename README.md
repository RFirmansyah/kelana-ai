# KelanaAI — AI-Powered Travel Planner

KelanaAI turns a destination, a budget, a trip length, and a travel style into a complete
day-by-day itinerary — generated by Amazon Bedrock — and pairs it with a retrieval-augmented
("RAG") chat assistant for travel questions, grounded in a dedicated knowledge base.

**Live app:** https://kelana-ai-blush.vercel.app

## Features

- **AI itinerary generation** — day-by-day plan, budget breakdown, and transportation
  recommendation from a single form.
- **Ask Assistant** — a RAG-powered chat assistant backed by an Amazon Bedrock Knowledge Base,
  with source citations.
- **Trip management** — save, view, edit, and soft-delete trips, all scoped privately per user.
- **Authentication** — JWT-based auth, bcrypt password hashing, per-user data isolation enforced
  on every endpoint (403 on any cross-user access attempt).
- **Light/dark mode**, responsive UI, custom 404/error pages.

## Tech Stack

| Layer      | Technology                                                        |
| ---------- | ------------------------------------------------------------------ |
| Frontend   | Next.js (App Router), React, TypeScript, Tailwind CSS              |

## Project Structure

```
kelana-ai/
├── backend/
│   ├── main.py                 # FastAPI app, routes

    ├── components/             # Shared React components
    ├── services/                # Typed API client functions
    └── .env.example            # Frontend environment variable template
```

## Prerequisites

- Node.js 20+ and npm
- Python 3.12+
- A PostgreSQL database (a free [Neon](https://neon.tech) instance works well)
- An AWS account with Bedrock model access enabled for the model(s) you intend to use, and
  (optionally) a Bedrock Knowledge Base already created for the RAG chat feature

## Local Development Setup

### 1. Backend

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS/Linux

pip install -r requirements.txt

cp .env.example .env
# then edit .env with your real values (see Environment Variables below)

python migrate.py               # applies all pending migrations

uvicorn main:app --reload       # runs on http://localhost:8000
```

### 2. Frontend

In a separate terminal:

```bash
cd frontend
npm install

cp .env.example .env
# NEXT_PUBLIC_API_URL should point at your backend, e.g. http://localhost:8000/api/v1

npm run dev                     # runs on http://localhost:3000
```

Open http://localhost:3000 — register a new account, then start planning a trip.

## Environment Variables

### Backend (`backend/.env`)

| Variable                    | Required | Description                                                                 |
| ---------------------------- | -------- | ----------------------------------------------------------------------------- |
| `DATABASE_URL`               | Yes      | PostgreSQL connection string.                                                 |
| `JWT_SECRET_KEY`              | Yes      | Long random secret for signing JWTs. Generate with `python -c "import secrets; print(secrets.token_hex(32))"`. |
| `JWT_ALGORITHM`               | No       | Defaults to `HS256`.                                                          |
| `JWT_EXPIRE_MINUTES`          | No       | Defaults to `60`.                                                             |
| `AWS_REGION`                  | Yes      | AWS region for Bedrock, e.g. `ap-southeast-2`.                                |
| `MODEL_ID`                    | Yes      | Bedrock model ID used for itinerary generation, e.g. `amazon.nova-lite-v1:0`. |
| `KNOWLEDGE_BASE_ID`           | Yes      | Bedrock Knowledge Base ID for the RAG chat assistant.                         |
| `KNOWLEDGE_BASE_MODEL_ARN`    | Yes      | Full model ARN used by the Knowledge Base's `retrieve_and_generate` call.     |
| `AWS_BEARER_TOKEN_BEDROCK`    | One of these two | Bedrock API key (simplest auth method).                              |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | | Standard IAM credentials, if not using a bearer token.        |
| `FRONTEND_URL`                | Recommended | Deployed frontend origin, added to the CORS allow-list.                   |

### Frontend (`frontend/.env`)

| Variable               | Required | Description                                     |
| ----------------------- | -------- | ------------------------------------------------ |
| `NEXT_PUBLIC_API_URL`    | Yes      | Backend base URL including the `/api/v1` prefix. |

## Database Migrations

Migrations are plain `.sql` files in `backend/migrations/`, applied in filename order and
tracked in a `schema_migrations` table so each one runs exactly once:

```bash
cd backend
python migrate.py
```

Run this after pulling any change that adds a new migration file, and again after first
deploying to a new database.

## Deployment

The live instance is deployed as: **Vercel** (frontend) + **Neon** (Postgres) + a Python host
of your choice (backend). Any static/Python hosting combination works as long as the
environment variables line up — the steps below match what's actually running.

### 1. Database (Neon or any managed Postgres)

1. Create a Postgres database and copy its connection string into `DATABASE_URL`.
2. Run `python migrate.py` once, pointed at that connection string, to create all tables.

### 2. Backend

Deploy the `backend/` folder to a Python host — [Render](https://render.com),
[Railway](https://railway.app), and [Fly.io](https://fly.io) all support this with minimal
config; a plain VM/EC2 instance works too.

- **Start command:** `uvicorn main:app --host 0.0.0.0 --port $PORT`
- **Build/install command:** `pip install -r requirements.txt`
- Set all the backend environment variables from the table above on the host's dashboard —
  do **not** upload your local `.env` file directly to a git-connected deploy.
- Set `FRONTEND_URL` to your deployed frontend's exact origin (e.g.
  `https://your-app.vercel.app`) so CORS allows requests from it.
- Run `python migrate.py` once against the production database (either as a one-off shell
  command on the host, or as a release/build step, depending on the platform).
- In the AWS Bedrock console, make sure **model access** is granted for whichever model
  `MODEL_ID` and `KNOWLEDGE_BASE_MODEL_ARN` reference, in the same `AWS_REGION` you configured.

### 3. Frontend (Vercel)

1. Import the `frontend/` folder as a new Vercel project (Next.js is auto-detected).
2. Set `NEXT_PUBLIC_API_URL` in the Vercel project's Environment Variables to your deployed
   backend's URL, including the `/api/v1` prefix.
3. Deploy. Vercel handles builds and preview deployments automatically on every push.

### 4. Post-deploy checklist

- [ ] Backend `FRONTEND_URL` matches the frontend's real deployed origin exactly (including
      `https://`, no trailing slash).
- [ ] Frontend `NEXT_PUBLIC_API_URL` points at the backend's real deployed origin.
- [ ] `python migrate.py` has been run against the production database.
- [ ] Bedrock model access is approved for the configured model(s) in the target AWS region.
- [ ] Register a test account and generate a trip end-to-end to confirm the full chain works.

## Security Notes

- Never commit `.env` or `.env.local` files — both are covered by `.gitignore`, and
  `.env.example` files are provided as safe templates instead.
- If a real secret is ever accidentally committed, rotating it in AWS IAM (or wherever it was
  issued) is required even if the push was blocked — treat any committed secret as compromised.
- `JWT_SECRET_KEY` must be a long random value in any real deployment; the backend falls back to
  a hardcoded insecure default if unset and will log a warning if so.
